# KAT500 applet and Advanced tools — proposed design

Status: user approved for implementation and Mac/Windows deployment on 2026-10-13. Firmware updater and Command Tester excluded.

## Intended outcome

Provide a native KAT500 applet and configuration/maintenance experience in a separate AetherSDR PR, matching the KPA500 work in #5991. The user's full and Mini screenshots define the operating information to retain. Every configuration feature in the installed KAT500 Utility is tracked in [the feature matrix](public-feature-matrix.md). Raw Command Tester/macros and firmware update tools are excluded by the user's explicit decisions. Installed firmware identification, Debug and Verbose remain included.

Research and validation remain non-transmitting. The user authorized full non-TX testing on 2026-10-13: reversible relay/configuration changes may be tested with before-state capture and restoration. Tune, erase, restore and reset experiments use injected transport fixtures; real memories remain untouched. No automatic radio carrier is part of connecting, opening the applet, or following frequency.

## Approach

Recommended: a dedicated KAT500 implementation using the established Peripheral and CanonApplet surfaces, KPA500 state colors and interaction conventions. Keep KAT500 parsing and maintenance separate: its EEPROM regions, fault records, tuning behavior, and sleep handshake differ materially from KPA500.

A shared generic Elecraft controller would require restructuring the finished KPA500 work and would obscure those differences. A Utility launcher would be less work but would not provide the native, cross-platform applets requested. Neither is recommended.

Use a separate KAT500 branch. Keep #5991 unchanged. If #5991 remains unmerged, explicitly stack against its reviewed head and identify the dependency, then rebase when it lands. Refresh issue #4953 and claim it before product edits.

## Applet

- Applet-bar label **KT500**. Show after successful KAT500 identification; retain while that transport session remains open, including logical power-off or silence. Hide on transport closure. Detection must not be inferred merely from an open socket.
- Header: confirmed **ON/OFF** state button, band/frequency summary, Mini toggle. Unknown state is shown explicitly; silence is not OFF. Clicking the power control requests the opposite state and waits for readback.
- Primary controls in both full and Mini: **Tune / Cancel**, **Auto / Manual / Bypass**, **ANT 1 / ANT 2 / ANT 3**, fault status and **Clear fault**. Antennas unavailable on the current band remain visible but disabled with an accessible reason.
- Both modes retain last-observed SWR, bypass SWR, frequency/band, Amp key interrupt, Attenuator and physical Bypassed status. Mini removes secondary detail and menus, not these operating facts. Match the supplied Mini screenshot's information density while using AetherSDR's existing visual language.
- Preserve the distinction between Bypass mode and physical bypass, between tuner key-line interruption and amplifier RF, and between last-observed readings and present activity. VFWD/VRFL are ADC counts, never labeled watts.
- Full view adds a collapsible manual section: C/L numeric controls and eight relay bits each, capacitor side, bypass/attenuator/key-line requests, Memorize, frequency recall, and full tune without saving where supported. Explain that manual relay/frequency changes can change the signal path.
- History: optional expanded SWR and forward/reflected-count graphs. Show gaps for missing samples; retain last-observed semantics and freshness. Put graph explanation in Settings, not a permanent footer.
- Settings: identity, firmware, serial, DIRECT/NETWORK endpoint, baud where applicable, freshness, normal/Verbose debug with copy/save/clear, and **Open Advanced settings**. Normal debug emphasizes state changes/errors; Verbose includes polling/wake traffic.
- Responsive layout: aligned compact controls, bars stretch horizontally, no large vertical gaps. Full, Mini and popped-out surfaces scroll vertically when their content exceeds available height. Preserve keyboard navigation and accessible state/value descriptions.

Follow TX frequency can use the existing effective TX-slice context when explicitly enabled. It must be distinct from actual transmit activity and from tuner Tune. Opening/connecting must not restore an old tuner mode, antenna, relay combination, or frequency over current hardware state. The initial implementation should not silently add an enabled-by-default frequency-write behavior for KAT500 merely because KPA500 has that preference; the earlier default approval was for the amplifier.

## Peripherals → KAT500 → Advanced

Use one scrollable detail surface with sections/tabs and the same applet shortcut pattern as KPA500. Show device identity and operation status at the top.

### Configuration

Read device values before editing. Keep staged edits separate from confirmed values. Apply writes only changed fields and verifies each setting by GET readback. Cancel discards staged edits; reconnect never replays them. Partial failures report what was confirmed and what remains unresolved.

Include all seven Utility categories:

1. Amplifier key interrupt power, including an explicit Optimize for KPA500 action. 1500 means unlimited interrupt threshold, not a transmit-power target; never apply it merely because a KPA500 is present.
2. Power on when DC is applied.
3. Sleep when idle, with wake-handshake handling.
4. Enabled antennas and preferred antenna for every band or All bands. Preserve mixed values until that field is deliberately edited; validate preferred antenna against enabled antennas.
5. ATU settings per bin for all eleven bands, 1–6. Explain six physical slots are shared among the antennas.
6. Auto-tune, bypass and amplifier-key-interrupt SWR thresholds per band/All. Mixed values remain mixed; fixed-point readback is authoritative.
7. Auto fine tune per band.

Keep documented additional tuner parameters and memory inspection in a small advanced/diagnostics subsection, with firmware availability reasons when unsupported.

### Backup and restore

Native `.KAT500Config` interoperability, complete data and checksum validation, bounded parsers, atomic file save, identity/firmware preview and an explicit restore confirmation. A complete backup contains both EEPROM regions, not just the visible configuration settings. Fault history is included in backup but must be excluded from restore, as the Utility help specifies.

Restore must use observed and verified allowed ranges, have fresh idle/no-RF preflight, suspend ordinary polling, allow cancellation between blocks, and stop on timeout/disconnect/identity change. No automatic write retry, reconnect replay, or reboot. Require readback verification before reporting completion. Do not enable a guessed range or claim restoration support from a valid file checksum alone.

### Fault history

Read on request, newest first. Columns: slot/index, elapsed device time, decoded fault, useful diagnostics and raw data. Distinguish Power On records from current FLT0. Preserve unknown codes and raw bytes. Export CSV. Fault clearing in the applet clears the current fault; it must not imply erasing history.

### Memories and reset

Inspect stored matches without confusing memory-row AN/C/L fields with live tuner state. Selective erase by band and antenna, with a preview of the target. Separate explicit factory-reset confirmation and baud/reconnect explanation. Neither erase nor reset runs on connect or settings-page open.

### Firmware identification and official Utility

Show the installed firmware version alongside model and serial in Peripherals, applet Settings and Advanced. Use that readback for compatibility checks and diagnostics. If the device identifies as bootloader (`kat500` rather than application `KAT500`), show that normal operation is unavailable and direct the operator to Elecraft's official Utility.

Firmware downloading, available-version checks, local image selection, flashing, bootloader entry and recovery tools are outside this PR. Users update firmware with Elecraft's official software, consistent with the KPA500 feature scope. Include a simple official Utility/help link, without an embedded updater or update-status polling.

## Transport and internal boundaries

Support local serial with the four documented rates and raw TCP for ser2net/aether-serial-bridge. Show DIRECT versus NETWORK accurately. The bridge owns serial baud and line settings for TCP. Raw TCP support does not imply compatibility with Elecraft Remote's separate authentication/session protocol; the companion bridge supplies remote serial access.

Keep protocol parsers, bounded frame buffering, serialized request/reply scheduling and maintenance state machines in libaethercore. Expose typed status/operations through a model facade for the GUI; do not add new direct GUI-to-core connection headers or backend-family branches. No additional thread is needed for the Qt serial/socket timers.

One connection owns the transport. Classify operation replies before telemetry: EEPROM and compound memory replies cannot update live controls accidentally. Preserve case where identity requires it. Wake with null commands, limit outstanding traffic, use slow power probes when off, and cancel pending mutations when the session changes.

Persist only client-owned preferences in one feature object: layout, Mini/history/debug choices and connection settings. Hardware-persisted configuration stays on the tuner. Never save it as a reconnect restore cache.

## Validation and review evidence

- Protocol fixtures from official documentation and original runtime wire observations; source/provenance and synthetic-versus-hardware boundaries retained.
- Parser tests for chunked/combined input, malformed frames, overflow, unsupported values, late replies and memory-versus-live routing.
- Stateful virtual serial/TCP tests for wake, timeout, off probing, reconnect, identity changes, canceled writes and exact maintenance ranges. Negative tests must demonstrate no replay and no success on partial backup/readback failure.
- GUI tests and screenshots at narrow/wide sizes, Mini/full/pop-out, history+debug, mixed-band configuration, disconnected/off/stale states, and Advanced navigation/lifetime.
- Native Mac and Windows builds, focused Linux verification and required CI/docs checks before review readiness.
- ms300prd desktop test build and Mac bridge screenshots after build validation. Physical evidence remains read-only and explicitly separate from simulator write tests and RF operation.

## Evidence still required

The help inventory and native backup/fault read captures are complete enough to specify the UI. The isolated Utility restore ranges are now captured (see [runtime findings](runtime-findings.md)); remaining required work includes stateful restore/readback verification, selective erase/reset sequencing, setter/mixed-value edge cases, sleep/off cadence, and original AetherSDR implementation/tests. These are outstanding work, not feature exclusions.
